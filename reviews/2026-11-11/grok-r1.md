## B. Design calls

**Local history in localStorage.** Move the blobs and commits to IndexedDB. Keep the zustand slice as the open branch, the index, and the remote map. What breaks first is two tabs, at any size, because the whole key is one string and the last tab to flush wins. Next is the quota, around 5 MB, because every version of a file is stored twice (once on the file, once as a blob) and the emergency save refuses to drop the blobs. The 50-commit ceiling is already breaking correctness on ordinary use, before the quota does, on a project that commits often and stays small. IndexedDB removes the reason for that ceiling. It does not fix `trim`. Keep a byte budget and garbage-collect blobs that nothing reachable references, after the parent walk in finding 1.

**Server-side `GITHUB_TOKEN`.** Right model for this app: the browser never sees the token, and the access key stays the gate on `127.0.0.1`. The current `repo` scope is the wrong token. The cookie is a 30-day bearer credential for every repo that token can touch, and the request body chooses the repo. Guardrails, in order: a fine-grained token with Contents read/write on named repos only; an env allowlist the handlers refuse to leave; fast-forward only, with the empty-repo placeholder as the single force update, checked afterwards; the fetch body cap from finding 6; no token in logs or error strings (this part is already true). Do not accept a GitHub token from the browser, and do not widen the cookie to a non-localhost bind without `COOKIE_SECURE` and a shorter max-age.

**Pull.** Stop replaying commits. Fetch the tip tree (the trees API, or the tarball clone already trusts), write one local commit "sync from GitHub at `<sha>`" with that tree, and three-way merge it with the previous synced sha as the base. Fast-forward is "the working tree becomes that tree". Diverged is one merge of two trees. Commit messages between the two shas can be a list on the side if you want them in the log. Replay costs a compare, a commit-detail call, and a blob call per file, and it is wrong for merges, date order, and skipped files. The extra history is not worth a tree that then gets pushed.

**Splitting `store.ts`.** Yes, along the async edges, and not before. Four modules: persistence and migration; git and the GitHub calls (`applyGit`, push, pull, clone), which is where a branch lock has to live; chat streaming; swarm. The store file stays the facade the components already call. Vault, prompt, and git pure functions are already out. A cosmetic split of the UI fields does not fix findings 3 and 4. Do the git module as part of those fixes so the lock and the remote-tip map have one owner.
