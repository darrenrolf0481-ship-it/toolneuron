EVIDENCE SHEET (what I ran since round 1; every item below was executed against the real code or the real GitHub API, not just read)

E1. LIVE on a private throwaway GitHub repo: a pull -> merge -> push reverts a file the app never copied.
    Steps: GitHub had asset.bin (binary, so clone skipped it). Linked clone. On GitHub, asset.bin changed v1 -> v2. Locally: edit README, commit, `git pull` (clean merge, "Not copied: asset.bin"), `git push`.
    Result: GitHub asset.bin was v2 before the push and v1 after it. The merge commit (parents: local commit, GitHub's commit) was built with base_tree = the FIRST parent's tree plus the local diff, so every file the browser does not hold (binary, >200 KB, beyond the clone's 300-file / 1 MB limit, ignored folders) silently takes the old side.
E2. Repro: switchBranch / mergeInto / pull overwrite an UNTRACKED working file when the target tree has the same path. `dirty()` only looks at staged and tracked-unstaged changes. (git refuses in this case.) abortMerge then deletes that file because HEAD has no copy.
E3. Repro: replayRemote gives the wrong tip tree when GitHub's history contains a merge. Fetch returns each commit's files as a diff against its FIRST parent, in compare order. History: A (main) sets f="A"; side branch: B1 sets f="B1", B2 reverts f to base; M merges, f stays "A". Replay order A, B1, B2, M ends with f="base". GitHub has f="A". (Note: a file ADDED on the side branch is not lost, because the merge commit's first-parent diff lists it. The failure is a side-branch change that the merge result does not keep.)
E4. Repro: after `clone main at M` -> push commit F to a new GitHub branch `feature` -> fast-forward local main to F: pushPlan(main) says "Everything up-to-date" although GitHub main is still M. One more commit G on main: expectSha = sha(F), the server sees main at M and rejects it as not a fast-forward; pull compares F...main, GitHub is "behind", nothing to pull. main can then neither push nor pull.
E5. Repro: two diverged branches, 60 commits on one. trim keeps the other branch's head but drops its parents; mergeBase() returns undefined; mergeInto falls back to an empty base and reports a conflict in a file only one side changed.
E5b. Repro (Grok's variant): commit A on GitHub; `feature` stays at A; main deletes a.txt and makes 55 more commits. pushPlan(main) returns "part of this history was trimmed ... cannot be pushed" (main can no longer push at all), and merging feature into main silently puts a.txt back and reports a conflict in b.txt, which only main changed.
E6. Measured: commit ids are the first 7 hex chars of the 14-char cyrb53 string, whose first char is only ever 0 or 1 (the high word is 21 bits). That is about 25 bits, not 28. 4 collisions in 20,000 ids. replayRemote skips inserting a commit when its id already exists and still maps the GitHub sha to that id.
E7. Fuzz: merge3 against `git merge-file` (git 2.43), 4,000 random three-way cases. Both clean: 1,900, text identical in all 1,900. Both conflict: 1,254. Mine clean but git conflicts: 846 (all are edits on ADJACENT lines, which git treats as a conflict and merge3 merges). Git clean but mine conflicts: 0. Crashes: 0.
E8. LIVE: the unlock lockout keys on getRequestIP({ xForwardedFor: true }). h3 returns the first X-Forwarded-For entry when the header is present. 7 wrong keys with one spoofed address: locked after 5. 12 wrong keys with a different spoofed address each time: never locked. The same key feeds the per-minute AI and GitHub limits. hit() also clears a whole map once it holds more than 5,000 keys.
E9. Test: pushPlan with a merge commit whose second parent is neither on GitHub nor in local history returns the string "part of this history was trimmed ... cannot be pushed". The stack walk visits parent2 as well as parent, so `{ index: undefined }` is not reachable.
E10. Test: a fetch AbortSignal also aborts a slow BODY read after headers arrived (Node 22: reader.read() rejected with TimeoutError at 1,504 ms for a 1,500 ms signal). clone.ts's 60 s signal therefore covers readCapped.
E11. Measured: a 129-file linked clone plus one commit serialises to about 2.1 million characters of localStorage.
E12. Read: store.ts createItem / renameItem accept duplicate sibling names and names containing "/"; git.workingFiles() keys by path, so duplicates collapse to the last one.
E13. Read: stream-chat.ts never checks response.ok or that a `done` event arrived; a non-NDJSON body returns { ok: true, text: "" }.
E14. Read: prompt.ts uses `state.draft || file.content`, so an emptied editor sends the old saved text; only the open-file section is clipped to the budget, the head (persona up to 4,000 chars, skills 1,600, handoff 2,400, knowledge 1,800) is not, and the server then cuts at 8,000.
E15. Read: git.markPushed writes track[git.branch] using the branch that is current when the response arrives; gitPull merges into the branch that is current when the response arrives.
E16. Read: fetch.ts checks a blob's size only after gh() has downloaded and JSON-parsed the whole base64 body, so one 100 MB blob in a pulled commit is fully buffered on the small VM before it is "skipped".
E17. Read: push.ts takes file modes from the first parent's GitHub tree once and reuses them for content writes, so text written at a path that is a symlink (120000) or submodule (160000) on GitHub is pushed with that mode.
